BYG Project

Making a BYG Video

How an illustration goes from idea to deployed video — the three phases, who does what, and how to batch them for production efficiency.

🗺 Overview

Each BYG illustration video goes through three distinct phases. These phases are intentionally separate — different modes of work, different tools, different who's-doing-what. Keeping them separate is what makes the process predictable.

The videos are built in Remotion — a framework that renders React components to MP4. The animation is SVG-based (hand-drawn style, dark background, spring animations). Narration is generated by Edge TTS (free, local, Microsoft voices) and saved as MP3 files that the composition loads at render time.

The key insight Audio drives timing. Each slide's duration is calculated from the exact length of its MP3 file (measured by mutagen, accurate to the frame). The video waits for narration, not the other way around.

✍️ Phase 1 — Script

1

Write the script and generate audio

All creative decisions happen here. No code, no Remotion. Pure content.

The output of Phase 1 is a notes.md file (content spec) and a set of MP3 files (one per slide + title) with a durations file that records their exact lengths in seconds.

What goes into notes.md

  • 1Both Narrative arc — one sentence: what is this illustration arguing?
  • 2Both 4 slide titles + subtitles — the structure of the argument across 4 beats
  • 3Both 3 bullet points per slide — written as final narration copy, ~20–30 words each
  • 4Both Doodle concept per slide — plain English description of what's in the scene at D0, and what appears at b[0], b[1], b[2]
  • 5Both Title card tagline — the hook question under the illustration title
Doodle descriptions matter "Hero on left, villain appears center-right at b[0]" is enough to build from. "Something interesting happens" is not. Specificity here saves back-and-forth in Phase 2.

Audio generation

  • 6Claude Write the Edge TTS generation script — one narration per slide + title card. Modelled on generate-white-hat-black-hat-audio-edge.mjs.
  • 7Tom Run the script: node scripts/generate-{slug}-audio-edge.mjs. Produces MP3s in public/audio/{slug}/.
  • 8Claude Measure exact durations with mutagen. Write the durations file: src/{slug}-durations.ts.
Why mutagen? Edge TTS produces VBR (variable bitrate) audio. File size is unreliable for duration estimation. mutagen reads actual audio metadata — accurate to milliseconds, which translates to frame-accurate timing.

Durations file format

// src/white-hat-black-hat-durations.ts export const WHITE_HAT_BLACK_HAT_DURATIONS_S = [ 18.432, // slide 1 22.016, // slide 2 19.840, // slide 3 21.248, // slide 4 ];

The title card audio is measured separately and used to set TITLE_FRAMES in the TSX file directly (audio duration in frames + ~19 frames buffer).

🖥 Phase 2 — Localhost

2

Build the composition and preview in Remotion Studio

This is where the video is assembled. Tom evaluates; Claude iterates.

The output of Phase 2 is a TSX file that looks right in Studio — timing correct, doodles correct, text readable. You say "looks good" and it moves to Phase 3.

  • 1Claude Copy NuclearPlant.tsx as template. Adapt slide content, bullet text, and title card from notes.md.
  • 2Claude Write the four SVG doodle components from the doodle descriptions in notes.md. Each doodle has a D0 state (always visible) and b[0]–b[2] states that spring in with each bullet reveal.
  • 3Claude Register the new composition in Root.tsx — import durations, calculate frame counts, add <Composition> entry.
  • 4Tom Open Remotion Studio at http://localhost:3001 and preview the composition. Studio should already be running; if not: cd Projects/Remotion/simple-narrated-slides && npm run start.
  • 5Tom Evaluate: timing, doodle legibility, text size, bullet pacing. Report what needs changing.
  • 6Claude Apply fixes — SVG coordinates, timing constants, bullet copy. Repeat from step 4 until approved.
What Claude can't do in Phase 2 Watch the video and judge whether it looks right. Everything else — writing SVG, adjusting timing constants, modifying text — Claude handles. Tom's role is visual evaluation and directing changes.

Key timing constants (in the TSX file)

ConstantWhat it controls
TITLE_FRAMESLength of the title card in frames. Set to: ceil(title_audio_seconds * 30) + 19
SLIDE_BUFFER_FRAMESSilence after each slide's audio ends. 30 frames (1s) for BYG illustrations.
bulletSpring delayWhen each bullet SVG element springs in, relative to slide start. Proportional to audio duration.

🚀 Phase 3 — Render and Deploy

3

Render the MP4, deploy to GitHub Pages, update the web app

Execution only. Claude handles everything; Tom watches and approves the final video.

  • 1Claude Run the render command from Projects/Remotion/simple-narrated-slides/:
npx remotion render WhiteHatBlackHat white-hat-black-hat-v1.mp4

Render takes a few minutes. CPU-bound, runs locally. Output goes to out/.

  • 2Tom Watch the rendered MP4. Confirm timing and visuals are correct.
  • 3Claude Create the wrapper HTML page — copy byg-nuclear-plant.html, update title, slug, and MP4 src. Save as apps/byg-{slug}.html.
  • 4Claude Deploy to byg-dev (staging) first using the byg-deploy skill — pushes MP4 + wrapper HTML to gh-pages.
  • 5Tom Check the live staging URL on ewallt.github.io/byg-dev/. Approve for production.
  • 6Claude Promote to byg (production) — same deploy to prod repo.
  • 7Claude Update behold-your-god.html — flip "Coming Attraction" badge to "▶ Watch", add link to wrapper page.
  • 8Claude Update project-definition.md — mark illustration complete with version number.
  • 9Claude Write illustrations/{nn}-{slug}/notes.md — record final script, doodle descriptions, and render/deploy log.
MP4 versioning Always version the MP4 filename on every deploy (e.g. -v1, -v2). GitHub Pages CDN caches aggressively — a new filename forces the cache to bust.

⚡ Batch Production Plan

Rather than taking each illustration through all three phases before starting the next, batch by phase. Each phase is a different mode of work — grouping them reduces context-switching and makes sessions more focused.

📝 Script Batch

  • Low token cost
  • Conversational — no tools
  • No auth, no servers
  • Do 3–5 at once
  • Output: notes.md per illustration

🖥 Localhost Batch

  • You at the screen
  • Studio running on :3001
  • Do 2–3 before fatigue
  • Output: approved TSX per illustration

🚀 Deploy Batch

  • Pure execution
  • Claude does most of it
  • Do all pending at once
  • Output: live videos on byg-dev / byg
Why this works Failures are contained. If a doodle needs rework in Phase 2, it doesn't block illustrations already deployed. If a script needs revision, no code has been written yet. Each phase has a clear completion state before the next begins.
