Infrastructure Project Reference

Cross-cutting tools, meta-processes, and housekeeping for the agent-test project.

🗂️ What This Project Is

Infrastructure covers everything that applies across multiple projects rather than belonging to one of them. It is not a deliverable — it is the maintenance layer that keeps the project coherent, consistent, and running well.

Three areas of concern:

Tooling — The task manager, git setup, Claude Code skills, and any scripts or utilities that support multiple projects (promote.sh, nlm CLI configuration, etc.).

Process and standards — How work gets done: testing, deployment, change management, documentation quality, and anything a well-run software shop would expect to have in place.

Housekeeping — Redundant files, stale documentation, overlapping tools, things that have drifted out of sync. Periodic cleanup to keep the project coherent.

Scope note Infrastructure work is defined by breadth, not depth. If something only matters to one project (e.g., a Remotion gotcha), it lives in that project's docs. If it affects how the whole shop runs, it belongs here.

🔍 Two Planned Reviews

When Infrastructure work begins, these two reviews scope the backlog. Each produces a list of findings that become tickets.

Review 1 — Redundancy & Cleanup

  • Files superseded by newer equivalents
  • Stale skills no longer in use
  • Dead or outdated documentation
  • Overlapping tooling (two things doing the same job)
  • Docs that exist in both .md and .html form but have drifted apart
  • Memory entries that are stale or incorrect
  • pending.md vs ticket board — any remaining overlap

Review 2 — Software Shop Standards

  • CI/CD — any automated checks on push/merge?
  • Test coverage — what's tested, what isn't
  • Onboarding documentation — could a new person get oriented?
  • Runbooks — how to start, stop, and recover each studio
  • Deployment procedure — is promote.sh enough?
  • Decision records — are architectural decisions documented?
  • Monitoring — any visibility into failures or drift?
Start here Do both reviews before creating tickets. The goal is a complete picture, not a long list of half-formed items. Review 1 often uncovers things that make Review 2 easier.

✅ Action Items

  • Agree on scope boundaries Decide what belongs in Infrastructure vs. individual project folders. The current definition is deliberately vague — make it precise enough to guide decisions.
  • Conduct Review 1 — Redundancy & Cleanup Audit the full repo. Capture findings as tickets with clear descriptions of what to remove or consolidate and why.
  • Conduct Review 2 — Software Shop Standards Assess against the checklist above. For each gap, decide whether it's worth filling now, later, or not at all — and ticket accordingly.
  • Prioritize the backlog After both reviews, sort the resulting tickets by impact and effort. Not everything needs to be done — the goal is a coherent, actionable list, not an exhaustive one.

🧱 Current State of the Shop

What's working well: The ticket board replaces pending.md as the live task tracker. The promote.sh script runs 99 structural tests before merging dev → main. Skills are organized at ~/.claude/skills/ with a clear SKILL.md convention. The session handoff system (handoff.md + session-log.md) provides continuity across conversations.

Known gaps: The two reviews haven't been done yet — so the full gap picture is still unknown. The scope of Infrastructure itself is still loosely defined. No CI/CD beyond the local promote script.

Good starting point The project already has more structure than most solo projects at this stage. Infrastructure work is about hardening and cleaning up, not building from scratch.
