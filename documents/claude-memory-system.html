Claude's Memory System

How Claude remembers things across sessions — what's stored, where it lives, and how it gets loaded.

🧠 Overview

Claude Code has a persistent, file-based memory system tied to each project. For this project, the memory directory is:

C:\Users\tomew\.claude\projects\C--Users-tomew-Documents-agent-test\memory\

Every file in this directory is a plain Markdown file. Claude reads them using the same tools it uses to read any file in the project. The difference is that one file — MEMORY.md — is automatically injected into every conversation. The rest are loaded on demand.

This is what gives Claude continuity across sessions: feedback you've given, decisions that were made, active notebook IDs, known pitfalls — all of it is written to files in this directory and read back the next time Claude starts.

⚙️ How Loading Works

1

MEMORY.md — always injected automatically

The index file. Claude Code reads this at the start of every conversation before you've said anything. It tells Claude where everything else is. It's deliberately short — just pointers and key facts — because it costs context on every session whether relevant or not.

2

Startup checklist — loaded at session start

MEMORY.md instructs Claude to read a small set of files at the start of each session: overview.md, handoff.md, and optionally CONTEXT.md, startup.md, session-log.md, and gotchas.md. These give Claude the current state of the project without loading everything.

3

On-demand files — loaded when relevant

Everything else is loaded only when that topic comes up. Domain-specific gotchas, feedback files, working notes — Claude reads them when they're needed, not upfront. This keeps each session lean.

Why not load everything automatically? Every file loaded at session start consumes context window space. Loading 20 files upfront — even if 18 are irrelevant — wastes capacity. The index-plus-demand model keeps context focused on what's actually being worked on.

🗂️ Types of Memory

Claude Code's memory system has four formal categories. Each file uses a frontmatter block to declare its type.

user

Facts about Tom — role, preferences, knowledge level, how to communicate. Example: "Tom goes by Tom. Session log entries are always written by Claude — never ask Tom to narrate."

feedback

Corrections and guidance Claude has received. Structured as: the rule, Why: (why Tom gave it), How to apply: (when it kicks in). These prevent Claude from repeating the same mistakes session after session.

project

Information about ongoing work — what's in progress, why, goals, decisions. Decays over time as work changes. Claude converts relative dates to absolute dates when saving so the memory stays interpretable later.

reference

Pointers to where information lives in external systems — a ticket board URL, a specific doc ID, a Slack channel. Helps Claude know where to look rather than where to store.

🚫 What Doesn't Go in Memory

The memory system is for information that can't be re-derived. These things should not go in memory files:

  • ✕ Code patterns and architecture — derivable by reading the codebase
  • ✕ Git history and recent changes — git log is authoritative
  • ✕ Debugging solutions and fix recipes — the fix is in the code; the commit message has the context
  • ✕ Things already in CLAUDE.md — no duplication
  • ✕ Ephemeral task details — in-progress work and current session context belong in tasks, not memory

✏️ Adding Your Own Memory Entries

You can ask Claude to remember anything at any time: "Remember that I prefer X" or "Note that we decided Y." Claude will write a new file and add a pointer to MEMORY.md.

You can also write files directly. The format is simple — frontmatter at the top, content below:

--- name: My Memory Entry description: One line — what this is and when it's relevant type: feedback --- The rule or fact goes here. **Why:** The reason behind it. **How to apply:** When Claude should use this.

After writing the file, add a line to MEMORY.md linking to it with a brief description. That's the only step required — Claude will read the linked file when relevant.

Keep MEMORY.md under 200 lines Lines beyond 200 are truncated during injection. If the index gets long, consolidate entries or move detail into linked files.

📋 Working Notes — Claude's Live Reference

working-notes.md is Claude's own quick-reference document, created to avoid reconstructing the same data from scratch each session. It's updated at shutdown and loaded when active work requires it.

It currently tracks: active notebook IDs, gdrive MCP integration status (token location, what works/doesn't, round-trip POC steps), notable Google Drive doc IDs, nlm CLI syntax gotchas, and ticket status at a glance.

Think of it as Claude's scratchpad for live data — the things that change session to session but are too tedious to re-derive by running commands.
