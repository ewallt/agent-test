Claude Code — Infrastructure Improvements

Identified from the 3/31/2026 source leak analysis. Ranked by leverage and implementation order.

📡 Background

On March 31, 2026, Claude Code's source was briefly published publicly. The developer community immediately reverse-engineered how the harness actually works — compaction strategy, the hook lifecycle, permission evaluation, agent frontmatter — and produced a wave of best-practices posts within 24 hours.

A NotebookLM notebook was built from that coverage (11 sources, dated 3/31 or later). The gaps below were identified by querying that notebook against this project's actual configuration.

🔧 Improvements — In Priority Order

1
Set AUTOCOMPACT threshold to 50%
Trivial

What: Add one environment variable to settings.json so auto-compaction triggers at 50% context usage instead of 95%.

Why: At 95%, the model is already cognitively overloaded when it compacts. At 50%, compaction is a clean, mid-task operation — the summary it produces is far better, and the remaining context stays high-quality for longer sessions.

{ "env": { "CLAUDE_AUTOCOMPACT_PCT_OVERRIDE": "50" } }
Risk: None. Purely a quality improvement. Do this first.
2
Add missing permission wildcards
Trivial

What: Add Bash(git *), Bash(npm run *), Bash(node *), and Bash(npx *) to the allow array in settings.json.

Why: Git is used constantly — committing, branching, promoting to main. Npm and node are used in every Remotion build. Without these, Claude prompts for permission on routine operations that are obviously safe. The leak confirmed: frequent permission prompts mean the config is incomplete.

"allow": [ "Bash(git *)", "Bash(npm run *)", "Bash(node *)", "Bash(npx *)", "Bash(PYTHONIOENCODING=utf-8 nlm *)", "Bash(powershell -Command *)", "Write", "Edit" ]
Note on Write/Edit: These currently allow any file. Acceptable for a solo developer trust context, but worth revisiting if scope expands.
3
Proactive /compact at task boundaries
Behavioral

What: Run /compact manually at natural task boundaries — when research is complete, when a feature is done, when switching projects, before a complex multi-step workflow begins.

Why: Auto-compaction is reactive — it fires when the window is nearly full. Manual compaction is proactive — you control when the summary is written, while context is still clean. The source leak confirmed this is the intended usage pattern: the harness supports it, but doesn't enforce it.

When to compact: After a notebook build completes. After a Remotion render. Before starting a new skill. At any "phase boundary" where what came before is settled and what comes next is a fresh problem.
4
Enable auto mode
Easy

What: Switch from skipDangerousModePermissionPrompt: true to launching with --dangerously-skip-permissions replaced by --enable-auto-mode, or configure it in settings.

Why: skipDangerousModePermissionPrompt is a blunt bypass. Auto mode is different: it runs a lightweight LLM classifier in the background that evaluates each tool use for intent, auto-approving safe actions and blocking injections and escalations. You get the same friction-free experience but with an active safety layer. The source leak revealed the classifier is configurable via autoMode.allow, soft_deny, and deny keys in settings.

Note: Investigate the exact settings.json key for enabling this — the leak revealed the internal keys but the CLI flag is --enable-auto-mode or toggle with Shift+Tab during a session.
5
Stop hook — autonomous build validation loop
Medium

What: Create ~/.claude/hooks/hooks.json and add a Stop hook that runs a validation script after each Claude turn.

Why: The Stop hook fires right before Claude finalizes a response. If your validation script exits with code 0, Claude stops. If it exits with code 2, the stderr output is automatically injected back into the conversation and Claude continues — fixing, retrying, iterating until the check passes. This is a zero-plugin autonomous loop, directly supported by the harness.

For this project, the most useful validation targets are:

  • Remotion: TypeScript compile check after scene edits
  • promote.sh: 99 structural tests before any merge to main
  • BYG: audio file existence check after narration generation
// hooks/hooks.json skeleton { "hooks": [ { "event": "Stop", "command": "bash ~/.claude/hooks/validate.sh", "description": "Run build validation after each turn" } ] }
Implementation note: The validation script needs to be context-aware — it should only run the relevant check for the current project. A simple approach: check which project directory is active and dispatch accordingly.
6
PreCompact hook — state snapshot
Medium

What: Add a PreCompact hook that saves a structured snapshot of session state before auto-compaction runs.

Why: When auto-compaction fires, the model forgets what files it was editing, what tasks are pending, and what decisions were made. A PreCompact hook can write a state file — active files, current task, recent decisions — before the summary is written. A SessionStart hook then restores this state at the beginning of the next session, so Claude never has to ask "what were we doing?"

This would complement (and potentially simplify) the existing startup skill and handoff.md system.

Design consideration: The startup skill already provides session continuity via handoff.md and session-log.md. The PreCompact hook adds finer-grained automatic snapshots between sessions. These are complementary, not redundant — the hook captures in-progress state; the startup skill provides narrative context.
7
Conditional rules — .claude/rules/ directory
Medium

What: Create a .claude/rules/ directory with YAML-frontmattered rule files. Each file specifies a glob pattern — the rules only load when Claude is editing files that match.

Why: Currently all CLAUDE.md content is injected on every turn, regardless of what Claude is working on. Remotion-specific rules load during a NotebookLM session; BYG rules load during a bar-chart-race session. Conditional rules eliminate this token waste — the right rules load at the right moment.

--- # .claude/rules/remotion.md globs: ["Projects/Remotion/**"] --- Always use `useCurrentFrame()` not direct frame variables. Never use CSS transitions — use Remotion's `interpolate()`. Check `start-studio.js` before touching composition registry.
Candidates for extraction: Remotion gotchas, BYG audio rules (Edge TTS only), nlm CLI syntax reminders, Playwright MCP patterns.
8
CLAUDE.local.md — private developer config
Easy

What: Create a gitignored CLAUDE.local.md at the project root for machine-specific configuration.

Why: Local ports, file paths, dev credentials, and machine-specific shortcuts currently either go into CLAUDE.md (polluting shared config) or stay undocumented. CLAUDE.local.md loads at higher priority than CLAUDE.md and is gitignored by default — the right place for things that are true on this machine but shouldn't travel with the repo.

Good candidates: Remotion Studio port (3000), ticket board URL (localhost:3010), local NLM binary path, any Windows-specific path overrides.
9
Agent frontmatter in skill files
Medium

What: Add YAML frontmatter to agent/skill markdown files to structurally constrain them using properties like tools, disallowedTools, model, maxTurns, and effort.

Why: The source leak revealed that Claude Code's agent system natively supports frontmatter-based constraints. Currently skills define their behavior entirely in prose — effective, but the model interprets rather than enforces. Frontmatter makes constraints structural: a read-only research agent literally cannot call Edit; a quick lookup agent cannot exceed N turns; a cost-sensitive scan can be pinned to Haiku.

  • High-value candidates: The Explore subagent (read-only, should never Edit), dialog-maker subagents (no file writes), NLM operator agents (constrained to specific commands)
  • Model routing: Pin fast/cheap tasks to Haiku, complex reasoning to Sonnet/Opus — currently everything runs on the session model
10
MAX_THINKING_TOKENS override
Trivial

What: Add MAX_THINKING_TOKENS: "10000" to the env block in settings.json.

Why: The default is 31,999 thinking tokens per request. For most tasks in this workflow — web app tweaks, Remotion edits, notebook operations — that's excessive. Dropping to 10,000 reduces hidden thinking costs by ~70% with no perceptible quality difference. Reserve extended thinking for genuinely complex planning tasks, which can override this locally.

"env": { "CLAUDE_AUTOCOMPACT_PCT_OVERRIDE": "50", "MAX_THINKING_TOKENS": "10000" }
Watch for: Any task where planning quality visibly degrades. If that happens, remove the override and evaluate whether per-task overrides are the right approach instead.

⚠️ What the Leak Says Not to Do

"STRICTLY ENFORCED" in all caps — The source code shows that CLAUDE.md is wrapped in an XML <context> tag alongside a hidden system disclaimer: "this context may or may not be relevant to your tasks." Shouting in all caps doesn't override this framing. Write instructions as architecture, not demands.

Starting fresh sessions for ongoing work — Long sessions accumulate structured memory: file lists, task specs, workflow state. Wiping this by starting fresh is a real cost. Use /resume or fork instead.

Using CLAUDE_CODE_EXPERIMENTAL_AGENT_TEAMS=1 — Not a real environment variable. Agent spawning works natively through the Agent tool. Don't add it.

Building custom TDD plugins — The Stop hook handles this natively. Exit code 2 feeds stderr back to the model. No plugin needed.
