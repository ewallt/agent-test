Reference Guide

NotebookLM Ephemeral Notebook Workflow

One fresh notebook per topic, built and populated automatically — from a topic description to a finished NotebookLM notebook with videos, in minutes.

? What This Is

NotebookLM is Google's AI-powered research tool. You give it sources (web pages, PDFs, text), and it lets you generate study guides, briefings, and short videos summarizing them. Each video covers a narrow focus angle — one argument, one concept, one thread of the topic.

The Ephemeral Notebook workflow automates everything that would otherwise be manual: creating the notebook, running research, importing sources, generating videos, and optionally building extra artifacts. You describe a topic; Claude does the rest using the nlm CLI.

The word "ephemeral" reflects the current phase of development — notebooks are treated as throwaway while the workflow itself is still being built and refined. Once the workflow matures, the notebooks may well be worth keeping long-term. The name describes a temporary posture, not a permanent design intent.

How to Start a Run

Say any of the following to trigger the workflow:

"run a notebook"
"run the ephemeral notebook workflow"
"run the notebook workflow"

Claude will load the master skill, read the workflow document, and execute the full run from the task file in tasks/.

🧩 Skills Loaded by the Master Skill

The master skill (notebooklm-ephemeral-notebook) loads sub-skills on demand based on task file flags. Each sub-skill is self-contained and loaded at the moment it's needed (JIT pattern).

Task flag Skill What it does
videos: N notebooklm-video Focus prompt and visual style guidance for NLM video generation
slides: yes notebooklm-slide NLM-native slide deck — generates and downloads as PDF
slideshow: yes notebooklm-slide-manifest Gemini slide manifest — written by Claude, uploaded as a notebook source
infographic: yes notebooklm-infographic NLM-native infographic — generates and downloads as PNG
app: yes notebooklm-webapp Standalone HTML web app built by Claude (Explorer + Quiz)

⇄ Inputs and Outputs

Inputs
A topic — what you want the notebook to be about. Can be a historical event, concept, puzzle, phenomenon, etc.
A task file (optional) — a short markdown file in tasks/ specifying key, topic, video count, and optional extras (app, slideshow, copied text).
A JSON request (optional) — a richer format in queue/ with search query, depth, style, and per-video focus guidance. Used for multi-notebook series or complex topics.
Copied text (optional) — a raw transcript or article pasted into copied-text/ when web research won't find the right source.
Outputs
A live NotebookLM notebook — created in your Google account with a permanent URL.
Sources — 5–10 web pages or documents imported into the notebook, which NotebookLM uses as its knowledge base.
Videos — one short AI video per focus angle (retro_print style). A three-video notebook covers three distinct angles on the topic.
Slideshow manifest (optional) — a markdown file of slide content generated by Gemini, ready for a Remotion narrated slideshow.
Web app (optional) — a standalone HTML file built by Claude that explores the topic interactively (e.g., a quiz, explorer, or infographic).
Run log entry — appended to run-log.md with notebook ID, URL, focus angles, elapsed time, and any hiccups.

→ The Four Phases

Phase 1
Task Definition
Deciding what to build and how to build it

You give Claude a topic. Depending on complexity, one of two paths is taken:

Simple path (task file): Claude reads or writes a short markdown file in tasks/. It specifies the topic, how many videos, and which optional artifacts (app, slideshow). This is the fast path for focused, single-notebook topics.

Rich path (JSON request): A JSON file in queue/ provides a full specification — search query string, depth, style, and detailed guidance for each focus angle. This is used for multi-notebook series (e.g., WW2 broken into four notebooks by theater) or when precise source-finding matters.

Focus angle design is the creative core of this phase: deciding which three (or one, or four) distinct threads of the topic each video will cover — so they're complementary, not overlapping.

Phase 2
Notebook Creation and Research
Building the knowledge base

Claude runs a sequence of nlm commands (always prefixed PYTHONIOENCODING=utf-8 nlm ...):

1
Create notebook nlm notebook create — creates a fresh notebook in your Google account and returns a notebook ID.
2
Run research nlm research add with a search query — NotebookLM searches the web and finds ~10 relevant sources. Alternatively, copied text is uploaded directly as a source.
3
Wait for processing Sources take a moment to index. Claude checks nlm source list to confirm they're ready before proceeding.
Known quirk: research imports sometimes report a timeout even when sources were actually imported. Checking the source count before retrying prevents duplicate imports.
Phase 3
Artifact Generation
Producing videos and optional extras

With the knowledge base ready, Claude generates the requested artifacts:

1
Generate videos nlm video generate — one call per focus angle, each with a specific guidance string telling NotebookLM exactly what to cover. Style is always retro_print. Typical run: 1–4 videos per notebook.
2
Download artifacts nlm artifact list then nlm artifact download — retrieves the finished video files. Slideshow manifests are downloaded the same way.
3
Build web app (if requested) Claude writes a standalone HTML file in apps/ — an interactive explorer, quiz, or infographic — using knowledge from the research. Not generated by NotebookLM; built by Claude from scratch.
Phase 4
Wrap-Up
Logging, housekeeping, and handoff

Claude appends an entry to run-log.md recording the notebook ID, URL, focus angles with source IDs, elapsed time, any interventions required, and hiccups observed.

The task file is moved from tasks/ to completed/. JSON requests are moved from queue/ to json-completed/.

The notebook URL is returned to Tom. The notebook is live in Google NotebookLM and ready to use.

Everything lives under Projects/NotebookLM/ephemeral-notebook/:

✎ Input Formats

Task File (simple, in tasks/)

A short markdown file — human-readable, hand-writable. Used for straightforward single-notebook runs.

key: braess-paradox topic: Braess's Paradox research: no copied-text: no app: yes slideshow: yes videos: 1 guidance: | Video style: retro_print. Focus on the core paradox and its counterintuitive implications for road networks.

JSON Request (rich, in queue/)

A structured JSON array — one object per notebook. Includes a precise web search query and per-focus-angle guidance. Used when a pre-processing AI (a separate Claude or Gemini session) has already designed the notebook plan.

[ { "topic": "The Black Death (1347-1353)", "videos": 3, "style": "retro_print", "format": "explainer", "depth": "deep", "query": "Black Death 1347 bubonic plague causes spread...", "guidance": "Focus on three angles: (1) origins and spread..." } ]

◈ Design Patterns

Single Notebook

One notebook, 1–4 videos, all on a tightly scoped topic. Best for a concept, event, or puzzle with clear boundaries. Each video angle approaches the same topic from a different direction — causes vs. lived experience vs. aftermath; psychology vs. mathematics vs. everyday applications.

Hume's Problem of Induction The Malthusian Trap Braess's Paradox Other Lane Paradox

Isomorphic Series

A large topic that is naturally divisible into a set of parallel items — all the same kind of thing, examined through the same lens. Each item gets one video; items are grouped into notebooks by a natural organizing principle. Notebooks are peers, not hierarchical.

The WW2 series is the primary example: four notebooks (Mediterranean, Eastern Front, Pacific, Western Europe), each with 3–4 battles as videos, organized by theater.

WW2 Battles (by theater) Scientific Revolutions (by field) Philosophical Revolutions (by era)

Claude as Source

Used when the topic is something Claude knows well and the subject matter is static — not dependent on current events, live research, or recent data. Instead of running nlm research, Claude writes the knowledge base itself and uploads it as the source. The notebook becomes a structured container for Claude's knowledge rather than a digest of external web sources.

The workflow differs from the standard path in two ways. First, source creation: Claude authors a tailored knowledge document — scoped precisely to the focus angles the video will cover — and uploads it as a plain-text source. Second, the task file sets research: no and copied-text: no; Claude's written document is the only source, and it is crafted for the job rather than scraped from the web.

This pattern is best when web research would return noisy, inconsistent, or shallow results for a topic that Claude can cover with depth and precision. It is also faster — no research phase, no source indexing wait — and produces tighter videos because the source is written to match the focus angle exactly. The notebook still gets a Gemini slide manifest and any other requested artifacts; only the source origin changes.

When to use it: well-established concepts, historical events, mathematics, philosophy, logic, science fundamentals — anything stable enough that Claude's training knowledge is a reliable and sufficient source. Avoid for anything time-sensitive, contested in current discourse, or requiring citation of specific real-world data.

⌨ The Key Tool

nlm is the notebooklm-mcp-cli (v0.3.2) — a command-line interface that talks to NotebookLM's API on your behalf. All commands are run through Claude's bash tool.

Every command is prefixed with PYTHONIOENCODING=utf-8 to prevent Unicode encoding errors from the CLI's styled output on Windows.

# Core commands used in a typical run PYTHONIOENCODING=utf-8 nlm notebook create → new notebook PYTHONIOENCODING=utf-8 nlm research add NOTEBOOK_ID "query" PYTHONIOENCODING=utf-8 nlm source list NOTEBOOK_ID → check sources PYTHONIOENCODING=utf-8 nlm video generate NOTEBOOK_ID → generate video PYTHONIOENCODING=utf-8 nlm artifact list NOTEBOOK_ID → find videos PYTHONIOENCODING=utf-8 nlm artifact download NOTEBOOK_ID ARTIFACT_ID

! Known Limitations

!
HTML files cannot be uploaded as sources NotebookLM only accepts URLs, PDFs, and plain text. Claude-built web apps can't feed back into the notebook as a source.
!
Report/slideshow download bug (v0.3.2) The artifact URL field is sometimes empty, causing downloads to fail. Slideshow manifests are accessible in the notebook UI but may not be downloadable via CLI.
!
Research import timeouts are often false The CLI may report a timeout even when sources were successfully imported. Always check source count before retrying — retrying duplicates all sources.
!
Auth expiry on long runs Google session tokens expire. On multi-notebook runs or slow sessions, Claude may hit an auth error mid-run. Tom re-logs in and the run continues from where it stopped.
