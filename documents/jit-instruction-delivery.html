JIT Instruction Delivery

How Just-In-Time gating prevents Claude from skipping steps mid-workflow — what the problem is, how the fix works, and where it falls short.

← Back to index

🧠 The Problem: Agent Drift

When Claude loads a skill or workflow at the start of a session, it reads all the instructions at once and forms a mental model of what to do. The problem is that this mental model degrades over time. As the conversation grows, earlier instructions compete with more recent context. Steps get compressed, reordered, or silently dropped — not because Claude doesn't know they exist, but because the model is working from a stale memory of what it read rather than the live document.

This is called agent drift: the gradual divergence between what the instructions say and what Claude actually does, caused by distance between when the instructions were loaded and when they need to be executed.

The insidious part Drift doesn't announce itself. Claude doesn't say "I'm skipping Step 2." It just moves on, confident it's following the workflow, while actually working from a compressed version of it.

🔍 A Real Example

During a session shutdown, the shutdown skill was invoked. The skill lists six steps in order:

1

Handoff discussion — ask Tom questions, write handoff.md

2

Session log entry — prepend new entry to memory/session-log.md

3

Pending update — mark completed items in pending.md

4

Ticket update — sync tasks.json

5

Git commit

6

Done message

Claude completed Step 1 (handoff discussion) and then jumped ahead, skipping Step 2 entirely. The session log was never written. It only got written later — when Tom asked "will you be in a good state after restarting?" — which happened to prompt Claude to think about what a restarting Claude would need, and the session log came to mind.

The step wasn't forgotten. It was in the skill. But there was nothing stopping Claude from moving past it, and drift did the rest.

⚡ What JIT Is

Just-In-Time (JIT) instruction delivery is a workflow design pattern where instructions arrive at the moment they're needed — not all at once upfront. Instead of loading the full workflow into context and hoping Claude remembers everything in order, each step explicitly surfaces its own instructions and requires a confirmation gate before the next step begins.

The key insight: instructions that are fresh at the moment of use are more reliable than instructions that were loaded earlier and must be recalled. The model isn't working from memory — it's working from the live document, right now, for this step only.

JIT was first applied to the NotebookLM Ephemeral Notebook workflow, where agent drift was causing source-focus mismatches and skipped artifact steps mid-run. It was subsequently applied to the shutdown skill after the session log incident.

🔧 How It Works in Practice

Each step in a JIT workflow has two structural elements that didn't exist before:

1. A ▶ STEP N header

Each step is labeled explicitly as a named stage. This makes the current step unambiguous — Claude knows exactly where it is in the sequence and can't conflate steps or execute them out of order without it being visible.

2. A ✓ GATE checkpoint

Each step ends with a gate that must be satisfied before the next step begins. The gate is a concrete, verifiable question: "Has this file been written? Has Tom confirmed? Has this command run?" Claude must explicitly confirm the gate before proceeding.

Before — numbered list

2. Session log entry (independent — synthesize from conversation, prepend to session-log.md)

→ Claude reads this, forms a mental note, and may or may not act on it

After — gated step

▶ STEP 2 — Session Log Entry

Write a new entry at the top of memory/session-log.md now — do not defer it.

✓ GATE: Session log entry prepended? → Proceed to Step 3.

The gate turns a passive instruction into an active checkpoint. Skipping it is no longer a silent omission — it requires Claude to either confirm completion or explicitly acknowledge that it hasn't done it yet.

✅ Why It Helps

Instructions are fresh at point of use

When Claude reaches Step 2, the Step 2 instructions are right there in context — not something to recall from 20 turns ago. The model is reading the instruction as it executes it, not retrieving a compressed version from earlier in the session.

Skipping becomes a visible act

In a plain numbered list, skipping Step 2 and going to Step 3 looks the same as completing Step 2 and going to Step 3 — there's no structural difference. With gates, skipping Step 2 means either lying about the gate or visibly bypassing it. The structure makes omission harder to do accidentally.

Steps stay isolated

JIT prevents Claude from mentally merging steps or deciding that "Step 2 and Step 3 are basically the same thing." Each step is a discrete unit with its own header, instructions, and gate. Boundaries are explicit.

No read-ahead compression

Without gates, Claude reads the whole workflow upfront and forms a compressed summary: "write handoff, write log, update tasks, commit." Steps that seem redundant or obvious get merged or dropped. JIT makes this impossible because each step only reveals itself when the previous gate is passed.

⚠️ Honest Limitations

JIT reduces drift — it doesn't eliminate the underlying tendency The root cause is behavioral: Claude has a tendency to work from a compressed mental model rather than the live document. JIT makes this harder to do accidentally, but it doesn't change the underlying model behavior.

Claude still has to read the workflow first

JIT requires Claude to start with the right file. If the skill isn't invoked, or Claude decides to "work from memory" instead of consulting the workflow, gates don't help. The first step — getting Claude to the workflow at all — still depends on correct triggering and session startup behavior.

Gates can be soft-confirmed

A gate says "confirm this is done before proceeding." But Claude can confirm incorrectly — either by genuinely believing a step is complete when it isn't, or by not checking carefully enough. Gates raise the bar; they don't make errors impossible.

Overhead per step

JIT workflows require more explicit confirmations and checkpoints. This adds some friction to execution — each step requires a beat of acknowledgment before the next begins. For short workflows this is fine; for very long ones it can feel mechanical.

Memory files don't prevent recurrence across sessions

A session log feedback note ("follow shutdown steps in order") helps remind Claude of the pattern — but memory files are read at session start, not at the moment the skill runs. The skill's own structure is the more reliable enforcement mechanism.

The right mental model JIT is structural guardrails, not a behavioral fix. It makes the right thing easier and the wrong thing more visible. It works best when the skill itself enforces the gates — not when Claude tries to remember to follow them from a note read earlier.
