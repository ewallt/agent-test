Playwright MCP — Findings & Notes

What we learned about browser-driven visual iteration: how it works, what it costs, when to use it, and what to build instead.

🎭 How Playwright MCP Works in This Project

Playwright MCP gives Claude a live browser session. Every navigation or interaction returns two things: an accessibility snapshot (structured YAML tree of all visible elements with refs) and optional screenshots. Element refs from the snapshot are used for subsequent clicks, fills, and interactions.

The browser session persists across tool calls within a conversation. If the Chrome window is manually closed by the user, the session dies and the next tool call will fail with a "browser process" error — the fix is to close Chrome completely and let the next navigate reopen it.

The snapshot cost problem Accessibility snapshots are returned on every navigation and click — you have no opt-out. For a complex multi-tab app, each snapshot can run 2,000–5,000 tokens. This accumulates quickly and is the primary driver of token burn in browser sessions.

Verdict: Not viable on Claude.ai Pro ($20/month)

The Pro plan limits are message-based (~45 per 5-hour window), not raw token-based. A visual iteration session with 3–5 tabs × 2–3 rounds each consumes 6–15 screenshot rounds plus large file reads — easily 80–150K tokens. That's a significant fraction of a day's budget spent on one feature.

Claude Max ($200/month) or API pay-as-you-go are the tiers where this workflow becomes viable. At $20/month, Playwright should be reserved for one-off verification at session end, not iterative debugging.

🔬 Effectiveness — Visual Iteration vs. Specification-Driven

The research finding is clear: visual iteration is the wrong primary tool for CSS theming. It can confirm that a change was applied, but it cannot audit whether all hardcoded values were eliminated, and it cannot guarantee consistency across tabs. The root cause of issues is structural (wrong selector, wrong specificity) — not visual.

We hit this directly: the Watch badge override failed because body.theme-explorer .badge-watch was outspecified by #illustrations-tab .badge-watch. No amount of screenshotting would have caught this — only a grep of the actual CSS would reveal the specificity conflict.

Visual iteration — weak for

Auditing whether hardcoded values are fully eliminated

Guaranteeing consistency across all tabs/components

Diagnosing CSS specificity conflicts

Maintaining design intent across sessions

Systematic work on deterministic tasks

Visual iteration — useful for

End-of-session sanity check (one screenshot per theme)

Catching obvious visual regressions

Verifying interactions and transitions

Exploratory prototyping

Anything where the output is subjective

The right methodology for CSS theming Audit hardcoded values systematically via grep or subagent scan → write all scoped overrides in one pass → verify with grep that no navy rgba values remain → one screenshot at the end per theme as a sanity check. No iterative screenshot loops.

📋 What a CSS Theming Skill Should Encode

The current gap: when doing CSS theming work, Claude improvises — what to look for, how to structure overrides, when to screenshot, how to handle specificity. A well-designed skill encodes all of this and the session runs in a single systematic pass.

Skill components

ComponentWhat it encodes
Color scheme referenceAlready exists in ux-color-schemes.md — exact hex values for all 4 themes
Audit procedureGrep/subagent pattern for finding hardcoded rgba/hex values in HTML/CSS; returns structured table of selector → value → theme mapping
Override rulesAlways use body.theme-X #tab-id .selector to beat tab-scoped specificity; never use body.theme-X .selector alone if the base CSS uses an ID
Mapping logicnavy rgba(139,185,255,…) → gold rgba(212,165,116,…) for Explorer; teal rgba(15,118,110,…) for Archives; etc.
VerificationGrep for remaining navy rgba values after applying overrides — not screenshots
Screenshot policyOne per theme, end of session only, to catch anything structural that grep can't see
The subagent audit pattern works Dispatching a subagent to scan all tabs and return a structured table of hardcoded values is the right core methodology. This should be Step 1 of the theming skill — not a one-off prep step, but the canonical first action every time.

🔭 Future Direction

What needs to improve before visual iteration is practical

Token economics: The workflow is architecturally sound. It needs model efficiency to improve — what costs 10K tokens today will likely cost 2K in a year or two. Revisit when that shift happens or when on a higher-tier plan.

The Playwright skill itself: The current skill doesn't tell Claude what to look for, how to verify, or when to use DOM snapshots vs. screenshots. A better skill would make sessions faster and more focused — the same way the BYG deploy skill makes deployment a single reliable command instead of an improvised sequence.

Skill self-improvement loop: The broader vision — models improving their own skills through structured feedback loops — is the right direction. The infrastructure (skill files, session logs, handoffs) is already in place. The bottleneck is cost per iteration, not architecture.

What worked well this session

Gear icon theme switcher — clean implementation, global body-class theming, popover with smooth transitions. Good pattern for future app theming.

Subagent CSS audit — dispatching an Explore agent to scan all 5 tabs and return a structured table of hardcoded values was fast and thorough. This is the right core methodology for theming work.

Global CSS variable override approach — setting theme variables on body.theme-X instead of scoped to individual sections is cleaner and more maintainable. All tabs re-theme automatically.
